# 公司双色球设计

## 范围

在 DZMM 多群玩法系统中新增一套号码型彩票「公司双色球」。它产生摸鱼币收支，复用现有的员工、余额、群聊开关、定时任务与后台配置能力，不接入玩法 gate（不是小游戏，不占用「当前游戏」）。号码池压缩为红球 01-10 选 4 + 蓝球 01-06 选 1，共 1,260 种组合，使头奖在群规模下约一个多月出一次，而非真实双色球的几十年。

**三个群共用一套经济**：期次、号码、奖池、调节金与开奖时刻全公司唯一，所有群买同一期、看同一组号码、同一时刻开奖；期号全局递增。公告广播到所有已启用监听的群。彩票是「公司」的，不是某个群的。

## 号码与概率

- 红球从 01-10 中选 4 个不重复号码，蓝球从 01-06 中选 1 个。
- 总组合数 `C(10,4) × 6 = 1,260`。

| 奖级 | 命中条件 | 概率 |
|------|---------|------|
| 一等奖 | 4红 + 蓝 | 1/1,260 |
| 二等奖 | 4红 | 1/252 |
| 三等奖 | 3红 + 蓝 | 1/52.5 |
| 四等奖 | 3红 | 1/10.5 |
| 五等奖 | 蓝球中且红球中 0-2 个 | 1/6.81 |

任意中奖概率 26.59%，每注期望返回 1.186508 摸鱼币。

## 群内流程

1. 每期开卖时生成红球与蓝球，写入期次并公布 `SHA256(号码串|盐)` 前 16 位；号码在停售前不对外返回。
2. 已入职员工在停售前随时购票。支持三种方式：`/购买彩票 03 07 09 10 + 05` 手选一注、`/购买彩票 机选 [注数]` 随机一注或数注、`/购买彩票 N 注` 进入引导逐注填写。
3. 每人每个北京时间自然日最多 5 注；同一期同一号码组合只能买一次；同一号码不得与本人本期已购重复，机选自动避让。
4. 开奖前 10 分钟停售（21:50），停售前 5 分钟在群消息冷清时发一次提醒；开奖时间 22:00。
5. 停售后当日 22:00 开奖：公布号码与盐，按员工合并结算，发放奖金后自动开下一期。
6. 开奖公告固定展示奖池余额、调节金余额与单人单期中奖上限。

## 奖池与结算

- 当期全部购票金额先进入奖池。奖池上限 200 摸鱼币，超出部分转入「调节金」，不再滚回奖池。
- 固定奖金：一等奖 100、二等奖 50、三等奖 15、四等奖 5、五等奖 1。
- 结算顺序固定：投注额入池 → 奖池封顶溢出 → 逐票判档 → **同一员工多张中奖票先合并** → 合并后**按员工封顶 100** → 应付超过奖池时可付款**按比例折算** → 发放。
- 折算发生在封顶之后；任何情况下不超发、不出现负余额、不允许系统凭空补币。
- 一等奖无人中时奖池余额自然滚存到下一期；因奖池有上限，实际表现为长期维持在满额附近。
- 首期由系统注入 100 摸鱼币作为启动奖池，之后不再额外注入，**全公司只注入一次**（不是每个群一份）；金额可在后台的「启动奖池」调整。
- 调节金与奖池各走一本账本，逐笔记录 `balance_after`，任意时点可对账。

## 全员福利

- **不自动发放**：定时任务与手动开奖只跑「停售 → 开奖 → 派奖 → 广播开奖公告」，福利必须在开奖之后由群内指令 `/发放福利` 手动触发。
- **只有核心董事会能触发**（`ranks.is_board`，与 `/发奖金` 同口径；Lv10 公司负责人也不行），未入职者回复先入职；权限判定与发放同事务，成功后写 `audit_events`（`event_type = company_lottery_welfare`）。
- 发放条件：总开关与福利开关开启 + 发送者是核心董事会 + 调节金 ≥ **当前已注册员工总数**（每人金额，默认 1 摸鱼币）+ 存在一期已开奖期次且晚于上次发放时刻。开奖后系统立刻开出下一期，所以判定比较 `drawn_at` 与上次发放时刻，不能看期次状态。
- 触发时每位已入职员工 +1 摸鱼币，调节金扣除相应总额。
- **每次指令只发一轮**，不是能发几轮发几轮；余数保留，参与下次触发。
- 门槛始终取最新注册人数，员工数变化后下一次触发即按新人数计算。
- 发放不开活跃度、不按投入比例，纯按人头；员工数为 0 或每人金额为 0 时不放行。
- 发放全程在一个事务内完成（判定权限 → 读余额加锁 → 判定 → 全员加币 → 记明细 → 扣调节金 → 写审计），中途失败全量回滚，重新发一次指令即可重试；同一期开奖后重复发指令不会重复发放。
- 回执区分 `group_only` / `group_disabled` / `disabled` / `not_joined` / `not_authorized` / `not_drawn` / `not_due` / `already_paid` / `paid`。
- 该机制使彩票整体既不增发也不回收货币：收多少发多少，唯一滞留是未达门槛的余数。

## 机选

- `/购买彩票 机选` 买 1 注，`/购买彩票 机选 N` 买 N 注；别名 `随机`、`机`、`random`。
- 机选直接下单，不进入草稿确认流程。
- 同一次机选生成的多注号码互不重复，并避开该员工本期已购号码与草稿内已有号码。
- 机选与手选共用每日 5 注限额，不额外放宽。
- 引导购票草稿中发送「机选」可为当前槽位生成一注，手选与机选可在同一草稿内混用。
- 机选与手选走同一个号码生成与判档函数，开奖判定不做任何区分；注单仅记录 `is_quick_pick` 供回执与后台统计使用。

## 管理与数据

- 后台提供彩票总开关、开奖时间与停售提前分钟、号码池与选球数、单注价格与每日注数上限、奖池上限与启动奖池、单人中奖上限、五个奖级的奖金、全员福利开关与金额。**发放权限不可配置**：固定绑在核心董事会职位（与 `/发奖金` 一致），后台也不提供发放按钮。彩票不接入玩法 gate，但每个群有独立的「开启公司双色球」开关，**只控制该群入口**；期次是全公司唯一的，开奖公告作为公司级公共信息广播到所有开着监听的群，不受彩票开关与「接收定时活动/公告」影响。
- 后台可查看期数、号码、投注额、中奖者、派奖、奖池与调节金流水、以及每位员工的累计投入与收益；并支持手动开奖与手动注资。手动开奖只对已过停售时刻的期次生效，避免在号码承诺期内提前泄露号码。
- 期次编号、奖池与调节金全公司共用一本账，不按群拆分：三个群的员工在同一个池子里买同一期，避免各群之间重复注入启动奖池，也避免同一时刻存在多组号码。
- 彩票是唯一「有系统净注入、奖池跨期滚存、还分两本账」的玩法，因此必须做守恒校验：每期断言 `期初 + 售票 = 派奖 + 溢出 + 期末` 与员工侧实发合计，账本写完后与期末余额复核，调节金断言 `发放前 = 发放额 + 剩余`；后台固定展示 `系统注入 + 售票 − 员工侧入账 = 奖池 + 调节金` 的对账结果。
- 彩票的余额流水**不计入「今日收益」与「今日收益榜」**：中奖与全员福利是零和再分配而非劳动收益，购票支出也不抵扣，否则一次头奖就能把人顶上收益榜。玩家自己的彩票盈亏看 `/我的彩票`（累计投入／累计中奖／净收益），全公司口径看后台彩票报表的对账。流水来源使用稳定 token（`company_lottery_purchase`、`company_lottery_prize`、`company_lottery_welfare`）。
- 帮助与知识卡说明购票指令、奖级概率、开奖时间与全员福利规则（含「开奖后由核心董事会发 `/发放福利` 手动发放」）；规则说明须如实写明长期期望返回约 1.19 摸鱼币。
- 不写入长期记忆，不产生玩家画像事实。
