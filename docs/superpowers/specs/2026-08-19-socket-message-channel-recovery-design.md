# Socket 消息通道与断线恢复设计

## 背景与根因

当前 Browser Worker 同时承担 Socket 实时收发、私聊发现、历史补偿和身份检查。
已登记私聊会被周期性加入历史补偿队列，Worker 还会在每次主循环调用
`user.getMe`。当平台的任一历史接口变慢时，主循环会延迟；紧随其后的身份请求
如果失败，又会被当成登录失效，最终让全部群聊停止领取出站消息。

2026-08-19 的线上故障中，系统在约两分钟内登记了 57 个历史私聊，随后读取一
个旧私聊房间时超时。六秒后 Worker 报告登录失效，吸烟室的德州扑克回复和主
群定时消息一起进入积压。德州扑克需要私聊底牌，因此更容易暴露问题，但并非
德州状态机或结算逻辑导致故障。

## 目标

- WebSocket 是健康运行期间唯一的实时消息入口。
- 各启用群持续接收新消息，某个群或私聊失败不能长期阻断其他群。
- 私聊只处理首次房间登记，以及正在进行的私聊玩法或投稿流程。
- 健康 Socket 期间不执行周期性全量历史扫描。
- Socket 断开后先重连，再对断线窗口执行一次有界历史补偿。
- 瞬时 HTTP 超时不能被当成登录失效。

## 非目标

- 不为普通私聊提供常驻 AI 对话。
- 不删除现有 `direct_chats` 映射或历史业务数据。
- 不新增消息代理、Browser Worker 实例或数据库迁移。
- 不改变德州扑克、蹦蹦数字炸弹、谁是卧底或投稿的业务规则。

## 通道职责

### WebSocket 实时通道

Socket 连接成功后，Worker 加入所有启用且允许监听的群聊，并接收这些群的新消
息。健康连接期间不通过 `chatroom.getMessages` 轮询群聊或私聊。

Socket 收到未知一对一房间的新消息时，只保存发送者与房间的映射。若消息是可
以从私聊直接发起的 `/投稿 随机事件`，则正常交给 Core；其他普通私聊不保存正
文、不调用 AI，也不回复。

### 已知私聊与活跃私聊

Core 分别提供两组房间：

- `known_direct_rooms`：`direct_chats` 中全部已登记房间，是用户与私聊房间映射的
  权威集合，但不等于监听集合。
- `active_direct_rooms`：当前确实等待私聊输入的房间，用于 Socket 订阅、入站放
  行和断线历史补偿。

活跃私聊集合由现有业务状态实时计算，至少包括：

- 未结束的随机事件投稿草稿作者；
- 正在收集数字的蹦蹦数字炸弹当前轮玩家；
- 正在发牌或牌局尚未结束的德州扑克玩家。

仅发送身份牌但不接收私聊指令的流程可以按出站消息需要临时加入目标房间，不
因此成为常驻私聊监听对象。流程结束、玩家退出或投稿终止后，对应房间立即从
活跃集合移除。

如果平台没有可靠的离开房间事件，Worker 可以保留本进程已加入的 Socket 房间，
但必须在入站边界按最新活跃集合丢弃非活跃私聊；下次重连时只重新加入活跃房
间。

## 首次私聊发现

新的一对一 `message:new` 事件是唯一发现方式。Worker 从事件本身取得
`sender_platform_id` 和 `chatroom_id`，先登记映射，再根据私聊准入规则决定是
否提交正文。

`chat.listAll` 不再参与消息监听或周期轮询。新房间映射依赖用户级 Socket 推送
的首条事件；重复事件通过数据库唯一约束和消息 ID 去重。

## Socket 断线与恢复顺序

Socket 断开时按以下顺序处理：

1. 标记 Socket 为重连中，暂停新的 Socket 出站领取；数据库中的出站记录保持
   `pending`，不丢弃、不确认。
2. 使用有限退避立即重连 Socket。普通网络失败保持重连状态，不进入人工登录。
3. 重连成功后重新加入全部启用群和当时的活跃私聊集合。
4. 对“全部启用群 + 重连时活跃私聊”各执行一次
   `chatroom.getMessages`，补偿断线窗口。
5. Socket 在历史补偿期间继续实时接收消息；实时事件与历史结果统一按
   `chatroom_id + message_id` 去重。
6. 每个房间只尝试一次历史补偿。单房间超时记录安全日志后继续下一个房间，不
   关闭 Socket、不切换登录状态，也不重启整个 Browser Worker。
7. 本轮补偿结束后不再扫描历史，直到 Socket 再次断开并成功重连。

必须先重连再补偿。若先扫描再重连，扫描结束与连接建立之间会形成新的丢消息窗
口。

## 身份与登录状态

`user.getMe` 只在首次建立浏览器会话或需要取得新 Socket 令牌时调用。健康
Socket 不进行逐循环身份轮询。

状态判断遵循以下规则：

- Socket 正常连接并已完成加入确认：保持 Ready。
- Socket 断开或请求超时：进入自动重连，不等同于退出登录。
- HTTP 超时、5xx 或网络异常：记录并重试，不进入人工登录。
- 平台明确返回 401/403、令牌接口明确无凭证，或页面明确回到登录页：进入
  `auth_required`。

平台请求错误必须保留状态码或错误类别，不能再把认证拒绝和普通网络错误都压缩
为同一个 `request failed`。

## 出站与跨群隔离

数据库继续按 `delivery_key` 保证同一目标内的消息顺序。不同群和不同私聊使用
独立 delivery key，可以并行发送。

某条消息发生 ACK 超时或内容拒绝时，只释放或失败当前出站记录。ACK 超时可以
触发 Socket 重连，但不能直接触发人工登录，也不能清空其他目标的执行队列。

Bot API 不在目标群时仍可降级为主账户发送；该降级只影响当前消息。吸烟室的德
州扑克发送失败不能阻止主群的命令回复、定时公告或随机事件消息。

## Worker 主循环

主循环只执行有界操作：

1. 同步启用群与 Core 计算出的活跃私聊集合；
2. 上报心跳和群连接状态；
3. 分派 Socket 已缓存的实时入站消息；
4. 按 delivery key 调度出站；
5. 若刚完成 Socket 重连，执行至多一个房间的历史补偿分片；
6. 运行定时任务。

健康连接期间第 5 步为空。任何一个平台请求都有硬超时，且失败后主循环仍能进
入下一轮。

## 可观测性

日志和管理端状态需要区分：

- `socket_connected`、`socket_reconnecting`、`auth_required`；
- 当前启用群数量、活跃私聊数量、待补偿房间数量；
- 每次断线原因、重连次数与重连耗时；
- 历史补偿的房间类型、耗时与结果，但不记录私聊正文；
- 各 delivery key 的 pending/leased 数量和最老消息年龄。

这些字段用于判断是平台断线、单房间补偿失败，还是某个目标的出站积压，避免再
把所有现象统称为“浏览器未登录”。

## 测试与验收

自动化测试至少覆盖：

1. Socket 健康时连续运行主循环，不调用 `chat.listAll`、
   `chatroom.getMessages` 或重复 `user.getMe`。
2. 未知私聊实时事件只建立映射；普通正文不持久化、不回复，私聊
   `/投稿 随机事件` 可以进入投稿流程。
3. 投稿草稿、数字炸弹收数和德州牌局中的玩家进入活跃私聊集合，流程结束后移
   除。
4. 非活跃私聊事件不会进入 Core 命令或 AI 流程。
5. Socket 断开后先重连，再恰好补偿全部启用群和当时活跃私聊一次。
6. 补偿与实时事件重复时只接受一条。
7. 单个私聊补偿超时后，Socket 保持 Ready，其他群仍能领取并确认出站。
8. `user.getMe` 的超时或 5xx 不进入人工登录；明确 401/403 才进入
   `auth_required`。
9. 吸烟室进行完整德州扑克行动时，主群的 `/余额` 和定时消息仍可在各自队列
   中发送。
10. 部署后两群保持 connected，Browser Worker 心跳持续更新，旧积压被清空，
    且至少观察一个完整德州回合无全局停摆。

## 上线与恢复

当前线上 Worker 已处于 `auth_required`，因此本次代码部署后仍需完成一次人工登
录。登录成功后按新的 Socket 恢复流程运行，不再依赖周期历史扫描。

部署保留现有 68 条 `direct_chats` 映射；它们属于已知集合，但只有满足当前活跃
流程条件的房间才会被监听或补偿。上线验证期间不删除积压出站，由 Worker 按原
顺序自动发送。
