## 0. 方案摘要

### 0.1 一屏看懂

**要解决的问题**：公司群是个每天打卡、摸鱼、开小剧场的地方，但**没有"人"的仪式感**——没人知道今天谁生日，寿星也拿不到任何表示。加一套"生日祝福"：当天自动祝福 + 发礼金 + 全公司可以随礼 + 寿星当天有点小特权。

**参与角色**

| 角色 | 能做什么 |
| --- | --- |
| 已入职员工 | `/设置生日 5-20` 登记；生日当天收祝福与礼金、享寿星特权；平时可给同事 `/随礼 20` |
| 同事 | 生日公告发出后的窗口内给寿星随礼，系统汇总播报 |
| 管理员 | 后台配开关/时刻/金额/折扣/文案；看生日名单与"谁还没填"；手动补发；**dry-run 测试触发** |

**一次生日的关键时刻**（以 5-20 生日、默认配置为例）

| 时刻 | 发生什么 |
| --- | --- |
| 5-19 20:00 | **预告**：「明天是某某的生日」（可开关） |
| 5-20 **09:00** | **祝福公告**：点名 + 祝福语 + 生日礼金 20 + 当天特权清单 |
| 09:00–10:00 | **随礼窗口**：同事 `/随礼 20` 转账给寿星（每人一次、单次 ≤20） |
| 10:00 | **随礼汇总**：「共 N 位同事随礼 X 摸鱼币」 |
| 5-20 全天 | 寿星特权生效：打卡双倍、购彩前 5 注免单、商店 8 折、随机事件完成奖励 +50% |
| 每年 | **每人每年只祝福一次**（唯一约束兜底） |

**改动边界**：新增独立的生日模块（5 张表 + 1 段 daily job + 4 条指令 + 1 个后台面板）。**既有玩法、经济规则、随机事件与彩票流程一行不改**，只在 4 个明确的挂点上读一个"今天是不是你的生日"的判断（见 §6）。

**经济性**：礼金是**公司发放**（新增货币）；随礼是**玩家之间转移**（不新增货币）；折扣是少回收；免单票是少回收。合计注入量可控（默认每人每年 20 + 最多 5 注票价）。

### 0.2 与"档案"旧决策的关系（要改一条）

`docs/superpowers/specs/2026-08-12-personal-profile-design.md` 明确写了档案**不拆分结构化字段**（第 5、63、151 行点名"生日"）。本次作为**唯一例外**：生日单独结构化存（否则无法可靠触发）。档案仍是自由文本，两者互不覆盖；`rule.md` 同步注明（见 §12）。

### 0.3 明确不做（本次 out of scope）

**AI 祝福（你定的「先不做 AI 相关的」）**、农历生日、私聊贺卡、生日当天自动发红包、年龄公开、生日改名/改档案联动。（跨群不再是排除项：三个群各自可开关，见 §3.7。）

### 3.7 群级开关（三个群各自可配）

- `group_chats.birthdays_enabled`（默认 `true`）：**只有开启的群**才收生日公告与预告；后台「群聊配置」页里可逐个关掉（与现有 `games_enabled` / `random_events_enabled` 同一套 UI 与接口）。
- 语义分工：

## 4. 触发与时序

### 4.1 `run_daily_jobs` 里加一段 `run_birthday_jobs(now)`

顺序：**随礼结算 → 预告 → 祝福**，都放在现有一堆 `run_*_jobs` 之后、群循环之前（与投票那段的相对位置无关，互不依赖）。每段都靠落库字段幂等。

| 段 | 触发条件 | 幂等锚点 |
| --- | --- | --- |
| 预告 | `preview_enabled` 且当前时间 ≥ `preview_time` 且**明天**有人生日 | `birthday_previews(user_id, preview_year)` |
| 祝福 | `enabled` 且当前时间 ≥ `greet_time` 且**今天**有人生日且 `visibility=public` | `birthday_greetings(user_id, greet_year)` |
| 随礼结算 | 存在 `tips_closed_at IS NULL` 且 `greeted_at + window ≤ now` 的记录 | `tips_closed_at` |

**广播范围**：只发给 `birthdays_enabled = true`、`listening_enabled = true`、`announcements_enabled = true` 且未删除的群，**每个群各发一条**；总开关 `enabled = false` 时三个群全静默。幂等记录 `birthday_greetings` 只有一份，所以「三个群都看到祝福、礼金只发一次」。

### 4.2 为什么"当天内补发"是天然的

任务每个 tick 都算一遍"今天生日 + 今年还没有祝福记录"。所以：**当天任何时刻 worker 恢复都会补发**（哪怕 23:59）；整天离线则静默跳过、不产生记录，明年正常祝福。**不需要**额外的补发状态机，也不需要"错过"标记。

### 4.3 2/29 与日期边界

- 平年没有 2/29：**按 2/28 祝福**（提前一天，不留空）。入职周年的 2/29 同理。
- 输入校验：`month/day` 必须是真实存在的日期组合（2-30、4-31 直接拒绝）；`year` 若填，校验 `(month, day)` 在该年存在（2/29 只允许闰年）。
- 时区统一用 `BEIJING`（现有 `BeijingDateTime`）。

### 4.4 与随机事件/公演的冲突

祝福公告是**系统公告**，不占用任何玩法活动状态、不受门禁影响（与彩票、投票公告一致）。但**寿星当天可能正在随机事件里**：
- `/随礼` 会被活动门禁拦 → 因此 `/随礼` 放进 `_RANDOM_EVENT_INDEPENDENT_COMMANDS`（§8.3）。
- 祝福公告不因为"活动进行中"而推迟（派发时点与玩法无关）。

## 5. 公告与文案

### 5.1 祝福公告（每个开启生日功能的群各一条，≤10 行预算）

```
【生日祝福】今天是 小明 的生日 🎂
入职 2 年 3 个月 · 现任 高级摸鱼专员 · 第 042 号员工
（祝福语一行，模板可编辑）
🎁 生日礼金 20 摸鱼币已到账
🎫 今天购彩前 5 注公司买单（发 /购买彩票 机选）
🏪 今天商店一律 8 折 · ✅ 今天打卡双倍
💐 想随礼的同事：/随礼 金额（最多 20，截止 10:00）
```

变量：`{寿星}` `{工龄}` `{职级}` `{工号}` `{礼金}` `{免单注数}` `{折扣}` `{打卡倍率}` `{随礼上限}` `{随礼截止}`。

### 5.2 预告公告

```
【生日预告】明天是 小明 的生日，想随礼的同事记得准备 💐
```

### 5.3 随礼汇总公告

```
【生日祝福·随礼】小明 收到 7 位同事的随礼，共 96 摸鱼币 💐
（随礼名单一行，太长则只报人数）
```

### 5.4 过滤与长度

- 公告过滤与彩票/投票**完全一致**：`deleted_at IS NULL AND listening_enabled AND announcements_enabled`；在此之上**只发给 `birthdays_enabled` 的群**（三个群可各自开关）。
- 群消息预算 1000 字 / 10 行；上面每条都 ≤10 行（名单过长只报人数，照候选公告的处理）。

### 5.5 模板可编辑

三段文案都进 `reply_templates.TEMPLATE_DEFINITIONS`（硬编码白名单，漏登记会运行时抛"未知模板场景"），后台"回复模板"页面可改；变量替换沿用现有机制。

| 特权 | 机制 | 挂点 | 幂等 | 经济影响 |
| --- | --- | --- | --- | --- |
| 生日礼金 | `_apply_balance_change(user, gift_amount, "birthday_gift", now)` | 祝福那一段（同事务） | `birthday_greetings` 唯一约束 | 注入 `gift_amount` |
| 打卡双倍 | `reward = rank.checkin_reward × checkin_multiplier` | `commands.py:1566` | 打卡本身的日唯一约束 | 注入 1 份基础奖励 |
| 购彩免单 | 生日当天**前 N 注免单**：`cost = 0`，`birthday_greetings.lottery_tickets` 累加，达到 N 后恢复原价 | `_company_lottery_purchase` 的 `cost` 计算（`repository.py:30168`） | 累加计数 + 入站去重 | 少回收 N×票价 |
| 商店折扣 | 生日当天结算价 = `price × discount%`；**展示价与结算价读同一个函数** | `purchase_shop_item`（`repository.py:26650`）+ `/商店` 渲染 | 无（按次享受） | 少回收 |
| 随机事件加成 | 寿星当次完成奖励 ×(1 + bonus%) | `repository.py:21789` | 无（按次享受） | 注入加成部分 |

**边界**：`visibility=private` 的人**不发公告、不发礼金、不享受特权**（他就是不想被提）；`enabled=false` 时全部不生效。

## 7. 随礼（社交层）

- **谁能随**：任何已入职员工（含寿星本人？**不能给自己随礼** —— 代码直接拒绝）。
- **金额**：1 ≤ amount ≤ `tip_max_amount`（默认 20）；整数；余额不足直接拒绝并提示。
- **次数**：每人每场生日**限一次**（`unique(greeting_id, from_user_id)`）。
- **窗口**：`greeted_at + tip_window_minutes`（默认 60 分钟）内有效；超时后拒绝并提示"随礼已结束"。
- **转账**：纯玩家间转移，两条流水（`birthday_tip_out` / `birthday_tip_in`），**不新增货币**；复用 `tip_random_event` 的"入站消息去重 + `with_for_update` 行锁"范式，防止同一条消息重复转账。
- **结算**：窗口结束时回填 `tips_count`/`tips_total` + `tips_closed_at`，播报汇总（§5.3）。
- **不做**：匿名随礼、附言、随礼榜排名、谢礼回执。
- 窗口、频率与上限都是默认值（我的建议，见 §14 第 4 条）。

## 10. 经济口径

| 项 | 口径 | 理由 |
| --- | --- | --- |
| 生日礼金 | **计入「今日收益」**（你定的口径） | 与打卡/游戏奖励同口径；寿星当天会因此排到日收益榜前面，属预期 |
| 随礼 | 计入双方流水（转出方为负、转入方为正） | 是玩家间转移；对**收益榜**的影响：转入方会被算成"收入"（同打赏，保持现有口径） |
| 购彩免单 | **不产生任何流水**（`cost=0` 时 `_apply_balance_change` 直接返回） | 少回收而非注入；不会影响收益榜 |
| 商店折扣 | 结算价变低，流水金额随之变低 | 少回收 |
| 打卡双倍 / 随机事件加成 | 计入收益（正常收入） | 是公司发的奖励 |
| 净效果 | **`today_income()` 一行都不用改** | 省掉一次对共享函数的改动，也就没有「动了收益口径影响别的玩法」的风险 |

**实现提示**：因为口径是「计入」，`today_income()`（`repository.py:24042`）**不需要任何改动**。测试仍要断言礼金确实计入了当日收益（防止以后有人手滑把它排除掉），并保留一条「其它 source 统计不变」的对照用例。

## 11. 边界与异常

| 情况 | 处理 |
| --- | --- |
| 整天离线错过 | 当天内自然补发；整天错过则静默跳过（无记录），明年正常 |
| 2/29 生日（平年） | 按 2/28 祝福 |
| 员工改名 | 公告读的是**当时**的 `display_name`，无需迁移 |
| 隐藏（`private`） | 不公告、不礼金、不特权；后台仍可见 |
| 改生日到"今天就生日" | 当天**立即生效**（下一次 tick 就祝福），不设"次日生效" |

| 随礼时窗口已过 / 余额不足 / 给自己随礼 / 重复随礼 | 各自明确提示，**不产生任何转账** |
| 彩票无开放期次 | 免单资格**留到当天有开放期次时再用**（资格按"当天 + 剩余注数"计，而不是按某个期次） |

| 管理员 dry-run | 绝不产生余额变动、绝不发公告、绝不写 `birthday_greetings` |
| 农历生日 | 不支持，文档说明"请自行换算成公历填写" |
