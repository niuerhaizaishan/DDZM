## 0. 方案摘要

把随机事件的"到点随机抽一个场景"换成**"提前公布候选 → 全公司投票 → 票高者当选"**；再给投稿作者一个付费推荐位，把自己的作品保送进候选列表（只买曝光，不买票数）。

### 0.1 总览（一屏看懂）

**要解决的问题**：下一场演什么，现在是系统到点随机定的，玩家只能被动接受。改成**全公司投票决定**；同时给投稿作者一个付费曝光位，让好作品更容易被看到。

**参与角色**

| 角色 | 能做什么 |
| --- | --- |
| 全公司已入职员工 | `/事件投票 序号` 投票（每人一票、可改票）；第 4 位广告作品同样可投 |
| 投稿作者 | 额外可买「事件广告卡」，把自己的作品送上第 4 个候选位 |
| 管理员 | 后台看票型与投票人明细；强制截止 / 改判 / **手动指定**兜底 |

**一次投票的关键时刻**（以 20:00 那场为例）

| 时刻 | 发生什么 |
| --- | --- |
| ≈16:20（上一场 16:00 场结束） | 建投票：抽 3 个随机候选 + 第 4 位"招商中"→ 全公司发**开投公告** |
| 16:20–19:50 | 投票开放；每 30 分钟**播报票型 + 提醒**；期间作者可用广告卡填第 4 位 |
| **19:50（开场前 10 分钟）** | **截止定稿**：票高者写进场次 → **定稿公告** |
| 19:55（开场前 5 分钟） | 原有的【随机事件预告】照常发出（此时事件名已定） |
| 20:00 | 到点开演：报名 → 进行 → 打赏 → 结束（**这一段链路完全没改**） |

**改动边界**：只替换"随机挑 1 个"这一步 + 新增投票/广告卡；开场、报名、进行、打赏、结束、发奖**全链路不动**。

**经济性**：买广告卡是正常扣币（货币回收，不进任何池子）；广告卡**只买曝光、不改票数**，能不能当选仍看投票。

> **播报频率提醒**：各场次间隔差别很大（02:00 场的窗口只有 ≈1.5 小时，10:00 场却有 ≈7.5 小时）。固定 30 分钟会让长窗口播 15 次，太吵。建议改成**自适应**：`间隔 = max(30 分钟, 窗口 / 6)`，即**每个窗口最多播 6 次**、且不短于 30 分钟。

## 2. 需求 1：全公司事件投票

### 2.1 数据模型（新增 3 张表）

**`random_event_polls`**（**全局唯一一份**）

| 字段 | 说明 |
| --- | --- |
| `id` | |
| `target_schedule_id` | 目标场次，**唯一**（一场次最多一份投票） |
| `status` | `open` → `closed` / `cancelled` |
| `opened_at` / `closes_at` / `closed_at` | `closes_at = 目标场次 scheduled_at − 10 分钟` |
| `winner_candidate_id` | 定稿后写入 |
| `announced_at` / `last_tally_at` | 开投公告、周期播报的**幂等占位**（沿用 `reminded_at` 那套） |
| `fallback_reason` | 零票/平票/候选不足时如实写进公告 |

> 因为投票是全公司一份，表上**不带 `group_chat_id`**；群信息通过 `target_schedule_id` 关联。
> 投票人资格 = **全公司已入职员工**（公告发所有群，谁都能投）。

**`random_event_poll_candidates`**（每期 4 位：3 随机 + 1 推荐位）

| 字段 | 说明 |
| --- | --- |
| `poll_id` / `position`（1–4） | `unique(poll_id, position)` |
| `source` | `random`（1–3）/ `ad_slot`（4） |
| `scene_id` / `template_id` | `unique(poll_id, scene_id, template_id)` 防重 |
| `scene_name` / `event_name` / `seat_summary` / `reward` / `target_rounds` | **冻结展示快照**，作者之后改稿不影响已开的投票 |
| `ad_slot_id` | 推荐位来源（可空） |
| `vacant` | 仅供第 4 位：**无人购买推荐位时置真，显示"招商中"且不可投** |

**`random_event_poll_votes`**

`unique(poll_id, user_id)`；字段 `candidate_id`、`created_at`、`updated_at`（允许改票）。
计票 = 每人 1 票，直接 `count(*)`，**不需要权重列**。
（`ranks.vote_weight` 目前只用于展示、全库无计票代码消费，本次不使用。）

### 2.2 时序

```
[上一场 ended / dissolved]
   └─ _finish_random_event 挂钩子 → 为"下一场 pending"建 poll
        ├─ 建候选 1–3（3 个随机场景）+ 第 4 位 vacant（显示"事件广告卡招商中"）
        ├─ ① 开投公告：3 个候选 + 招商中占位 + 截止时刻
        │     └─ 开投之后（截止之前）任何人都可以用事件广告卡填补第 4 位 → 补一条公告
        └─ 每 30 分钟 ② 票型播报 + 提醒（last_tally_at 幂等）
              └─ ③ closes_at = 开场前 10 分钟 → 定稿：票高者冻结到场次（复用现有
                 _set_random_event_schedule_snapshot）→ 定稿公告
                    └─ 开场前 5 分钟：现有的【随机事件预告】照常发出（此时事件名已定）
                          └─ 到点 _start_random_event_from_schedule 照旧
```

**关键：截止（T−10）必须早于现有预告（T−5），这样预告发出去的事件名已经是定稿结果。**

**广告卡的使用窗口**：只在 poll 处于 `open`（开投之后、截止之前）时可用；其余时刻（还没有 poll、已截止、已作废）一律**拒绝使用且不消耗卡**，提示等下一次开投。这样不需要"待生效"这种中间状态——确认即写入当前 poll 的第 4 位。

**两条开投路径**（缺一不可）：

- 主路径：上一场结束（`_finish_random_event`）→ 开投；
- **定时兜底**：距下一场 `scheduled_at` 不足 **30 分钟**而该场还没有 poll → 强制开投。
  因为 `in_progress` 没有任何超时分支，上一场可能永远不结束（`rule.md:91` 也承认跨天保留）。

**目标场次被跳过时（顺延）**：上一场若仍 active，到点的下一场会被标 `skipped`。此时 poll **顺延**到再下一个 `pending` 场次：改写 `target_schedule_id` 与 `closes_at`，**已投的票与已填入的第 4 位广告都保留**，并公告"本期顺延到 HH:MM"。

### 2.3 平票判定（按顺序）

1. **演出次数少**的优先 —— 复用现成的查询写法：按 `random_events.scene_name` 分组、只统计**已结束**场次（`ended_at IS NOT NULL`），见 `repository.py:3636-3643`（`list_random_event_submissions` 里已经在用同一套统计）；
2. 仍相同 → **投稿晚的**优先。投稿时间就取 `random_event_submissions.submitted_at`（`scene_id` 是场景与投稿之间**唯一**的关联，通过时写入，`repository.py:3835`）；
3. 仍相同 → **随机**。

三种判定的结果都要在定稿公告里如实写明（"平票，按演出次数较少选出"）。

**关于"后台自建场景没有投稿记录"（已核查）**：查遍全库，能追出作者的只有 `random_event_submissions.scene_id → user_id → submitted_at` 这一条链；`create_random_event_scene`（`repository.py:21046`）的签名里**没有任何作者/审核人参数**，也**没有任何场景级审计事件**（grep `event_type="random_event…"` 无命中）。所以后台自建场景只能退化为比较 `random_event_scenes.created_at`——两种时间口径统一按"时间晚的优先"比较。

### 2.4 候选从哪来（**严格沿用现有随机逻辑**）

3 个随机候选**完全复用** `_fill_random_event_schedule_snapshot`（`repository.py:22040-22097`）的选池与抽取规则，只是把"抽 1 个"变成"抽 3 个互不相同"。**不新造一套随机算法。**

1. **候选池** = 所有 `enabled` 场景（`22045-22049`）；
2. **排除两类**（与现状一致）：
   - 历史上已演过的场景（`RandomEventRecord.scene_name` 去重，`22052-22054`）；
   - 当天已排给**其它**场次的场景（`random_event_schedules.event_date` 相同、`scene_name` 非空、排除自己，`22055-22063`）；
   - **再加一条**：本次投票已经选定的另外两个候选（保证 3 个互不相同）；
3. **优先级分档**（与现状一字不差）：①"没演过且没排过" → ②该档不够就退到"没排过" → ③再不够就用全部；
4. 在命中的档里用**同一个随机源**（`secrets.randbelow`，`22078`）抽 3 个不同场景；每个场景再随机配 1 个事件模板（`22079-22088`）与席位（`22089-22095`）；
5. 某个场景**一个事件模板都没有**时跳过它另抽（对应现状的 `if not templates: return False`，`22086-22087`）；
6. 整个池子都不足 3 个时，按实际数量公示（2 个就 2 选 1），公告说明。

> **档位不足 3 个时的取舍**：允许**跨档补齐**——例如"没演过"的只剩 2 个，就从"没排过"那一档再补 1 个，尽量凑满 3 个候选；只有整个池子都不足 3 个才减少候选数。

> 因此"优先没演过的、其次没排过的"这个既有偏好**原样保留**：投出来的下一场，仍然优先是大家没看过的事件。

### 2.5 指令与公告

- **`/事件投票 序号`**（新增指令）
- `/事件投票情况` 查看当前票型（可选，播报已覆盖）
- **必须加进 `_RANDOM_EVENT_CONFIGURABLE_COMMANDS`**：门禁的允许清单只能从该白名单里选（`service.py:580-594`），不在其中就**永远无法放行**；而随机事件经常处于报名中/进行中，否则"上一场还在演，下一场的票投不了"。同时建议加进"报名中/进行中允许执行指令"的默认值。
- **公告目标群 = 按同事最新那版彩票口径**：`deleted_at IS NULL` + `listening_enabled` + `announcements_enabled`（即 `4a65a64` 之后 `_company_lottery_announce` 的过滤条件），候选公告、票型播报、定稿公告、广告卡公告**四类全部一致**。
- **公告文案与行数预算**（上限 10 行 / 1000 字，超了会被拆条）：

  ```
  【事件投票】20:00 那场演什么？（21:50 截止）
  1. 《天台上的月亮》 主持1/男1/女1 奖6
  2. 《加班的幽灵》 老板1/社畜2 奖6
  3. 《末班地铁》 司机1/乘客3 奖8
  4. 📣 事件广告卡招商中
  回复 /事件投票 序号
  ```

  7 行可容纳"3 个候选 + 招商中占位 + 投票口"。**身份列表过长时只显示人数**（如"4 人"），保证一行一个候选。第 4 位被买下后，同一份公告的模板换成具体广告行（作品名 + 身份 + 奖励 + 作者）。

### 2.6 边界与异常

| 情况 | 处理 |
| --- | --- |
| 场景库为空 / 候选凑不出 | 不建 poll，回退现有随机，公告说明 |
| 到点零票 | 回退随机抽 1 个，公告写明"无人投票，随机选定" |
| 平票 | §2.3 三级判定 |
| 目标场次被 `skipped` | **顺延**到再下一个 pending 场次，票与第 4 位广告都保留 |
| 群关闭「允许随机事件」 | 不建 poll；未结 poll 作废（顺延无目标时同样作废） |
| 公告范围 | 彩票当前口径（`listening` + `announcements` 双开关） |
| 场次间隔太短（00:00→02:00，窗口 ≈1.5 小时） | 播报间隔取 `min(30 分钟, 窗口/2)`，保证至少播 1 次 |
| 场次间隔太长（02:00→10:00，窗口 ≈7.5 小时） | 播报间隔取 `max(30 分钟, 窗口/6)`，**每个窗口最多播 6 次**，避免刷屏 |
| 每天第一场（00:00） | 由前一天 20:00 场结束触发开投，跨天衔接 |
| 管理员改期 / 删场次 | poll 跟着重算 `closes_at` 或作废 |

### 2.7 关键取舍：投票**不**新增 `random_events.state`

"活动中的随机事件"这套状态被硬编码在 **1 个部分唯一索引 + 8 个 Python 元组**里（`schema.py:1846-1852`；`repository.py:22182 / 21558 / 21261 / 20823 / 20873 / 11624 / 2840 / 12012 / 4112`），还牵动 `_finish_random_event`（同一字符串写进 `event.state` 与 `schedule.status`）、历史筛选 `Literal`（`app.py:3035-3038`）、`classify_random_event_message`、`active_gameplay_summary`、`force_end_gameplay`。

**所以投票做成挂在目标场次上的独立对象：场次在定稿前一直是 `pending`，投票期不占用 active 状态。** 好处：不动唯一索引与状态元组；投票期间**不阻塞**该群开别的游戏；不需要改那四个函数。代价就是 §2.2 的定时兜底。

### 3.3 效果与拒绝规则

- 填入**第 4 号候选位**（3 随机 + 1 广告卡），**是全公司投票的正式候选之一**（决策 21）：`/事件投票 4` 可以投它，票最高就演它，**票数不额外加权**。
- 开投时该位是 `vacant`，显示「📣 事件广告卡招商中」，此时**不可投**（序号 4 会提示"该位置还没有作品"）；被买下后才成为可选候选。
- **拒绝使用**（一律**不消耗卡**，且**必须给用户明确提示**，决策 22）。每条一个独立文案：

  | 触发条件 | 提示（写在私聊，不是群里） |
  | --- | --- |
  | 当前没有处于 `open` 的投票 | 「现在没有正在征集的期次，等下一次开投后再用。」 |
  | 选择的作品与候选 1–3 重复 | 「《X》已经在候选列表里了，换一个作品吧。」 |
  | 第 4 位已被别人占用 | 「本期的广告位已经被占用了，下次早点来。」 |
  | 自己还没有已审核通过的作品 | 「你还没有已审核通过的作品，先发 `/投稿 随机事件`。」 |
  | 草稿超时 / 已截止 | 「广告卡向导已超时，请回群重新发送 `/使用 商品编号`。」 |

- 校验在 `/选择` 时先做一次（即时反馈），`/确认广告位` 时再复查一次（防止期间被占），两次都要给提示。

### 3.4 消耗与退款

- **`/确认广告位` 成功即视为"已使用"，不顺延、不退回**（决策 10）。
- **投票顺延**（决策 17）时，广告是**已经写进那份投票的第 4 位**，会**跟着投票一起顺延**——这不是"补发"，只是同一份投票换了目标场次。
- 草稿超时未确认、或被上述任一规则拒绝 → 商品仍在个人库存，可再次 `/使用`。
